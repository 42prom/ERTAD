# Hierarchical work

The web console exposes `/tasks`. Authority comes from approved, current membership grants and unit ancestry, never an account's role label. `workitem.read` allows scoped discovery; `workitem.create` manages work and delegates within its scope; `workitem.participate` permits voluntary participation; `workitem.verify` independently confirms completion. All require current read access. Lower levels cannot act on ancestor or sibling work without a separate valid grant. No organization picker or member directory is introduced.

A task specifies its responsible unit, description, one configurable participant role, priority, place limit and deadline. Creation opens the task. Delegation creates an offer in an immediate child authority unit, reserving places against the parent's limit. The receiver accepts all or part of the allocation, or declines with a reason. Further delegation uses the same rules at every depth. Original ancestry is recorded: moved units lose access to stale tasks pending an explicit future reassignment workflow.

Migration 23 adds optional meeting place and start time (not later than the deadline), with the existing responsible-unit scope acting as the audience boundary. The web form defaults the role to Participant and priority to normal, places these in **Additional options**, and exposes an explicit approved reward choice or **No reward**. It does not add arbitrary audience selection outside that unit scope. Unused oversight/resource/funding panels are collapsible; configured criteria and needs remain visible and enforced. See [Contribution](CONTRIBUTION.md) for independently approved templates, frozen offers, inherited delegation and private reward history. A template does not grant professional qualifications or change verification permissions.

Participants volunteer before a manager selects them. The workflow is application → assignment → work in progress → submitted completion → independent verification. Managers may reserve applicants, reject them, record a no-show, or return submitted work for changes. Participants may withdraw before verification. Each progress update includes a percentage and note. Deadlines prevent new allocation and enrollment; already assigned work can be completed late and is visibly overdue. One application per person/task is retained; reapplication is not offered in this slice.

Allocated places equal active/verified individual assignments plus the capacities of non-cancelled child tasks. Organization transaction locks serialize competing changes; versions reject stale writes. Accepting fewer places releases the difference. Withdrawal and no-show release an individual place; reserves consume none. Completed children retain their allocations. A task cannot close while children or assigned work remain unfinished. Cancellation requires finishing/cancelling children first and cannot erase verified work or release its consumed capacity. There is no automatic deadline cancellation.

Events, retry receipts and verified Activity entries are append-only. The verifier cannot be the participant. Verification creates exactly one `task_completed` Activity entry for the assignment in the same transaction. This records participation, not points or authority. Notifications persist inside that transaction for affected participants and scoped managers; `/tasks` has an unread inbox and explicit mark-read action. It does not yet replace the appointment inbox or send email/push notifications. History shows the latest 100 visible events; all events remain stored. Ordinary participants see their own applications/events plus shared task events; managers see minimal member identifiers and progress, not private profile attributes. Demo labels are separately scoped synthetic projections.

Mutations require a current session, CSRF/Origin and recent password step-up, plus audited commands. The runtime database role has no direct access to the new tables. Audit failure rolls back state, notifications and Activity. Authorization and relevant deadlines are rechecked after audit. Retried commands bind actor, organization, operation and exact payload to a UUID key. The UI preserves uncertain requests and prevents competing edits until their outcome is known.

## Current boundary

### Operational oversight

Migration 11 adds a coordinator, weighted completion criteria, blockers and scope-filtered summaries to the same command transaction. Creation initially identifies the creator as coordinator; accepting delegated work makes the accepting manager accountable. Reassignment can select the actor or an eligible manager with current membership in the owning unit. It grants no permissions and cannot impose responsibility on arbitrary ancestor/sibling managers. Revoked coordinator access is visible as a gap instead of restoring grants.

Managers may define one to ten criteria, each with a positive weight. The definition freezes after the first application, non-cancelled child allocation or result submission, including a submission later returned for changes. Each criterion moves from pending to submitted to independently verified; a verifier may return submitted evidence for changes. The submitter cannot verify their own result, and their current contributor eligibility is rechecked through audit completion. Verified progress is the weighted fraction of verified criteria. Participant percentages remain self-reports, not official progress. A criteria-only task can finish with all criteria verified; this does not fabricate participant Activity or points. Individual assignment verification retains its existing Activity semantics.

Managers and currently assigned participants can report operational blockers with type, reason and next review date. The owner must be an eligible manager. A manager can update the owner/next action/review date without claiming resolution, or resolve with a recorded explanation. At most ten blockers may remain open; the detail projection includes open blockers and recent resolved records, bounded to fifty. Active blockers stop task completion, not all useful work. All defined criteria must also be verified before completion. Verified criteria cannot be silently discarded by cancellation. Financial/resource blocker categories report a shortfall; they do not implement financial or stock accounting.

The list has unit/subtree, blocked, overdue and needs-review filters. Counts include only currently visible tasks; parent summaries traverse visible descendants and count visible leaf tasks once. They do not average unrelated percentages or expose the existence/status of hidden child tasks. Coordinator choices expose only bounded opaque identifiers; the local demo resolves scoped synthetic labels separately. Criterion/blocker notes are shared operational information within task read scope and must not contain private evidence or identity data. History retains definition snapshots and changed identifiers with the normal immutable event/version. Private text reports now have a separate restricted disclosure path; richer proof formats, criterion-specific attachment linkage and correction/reversal of independently verified criteria remain future work.

Migrations 12–14 extend this card with people/resource/service needs, verified qualifications, external funding accounting with collective approval, and prospective contribution points. The concrete constraints and remaining extensions are documented in [Work operations](WORK_OPERATIONS.md) and [Contribution](CONTRIBUTION.md). See STATUS for activation and verification evidence.

This is an operational **task** journey for web users. Private text-report attachments are defined in [WORK_EVIDENCE](WORK_EVIDENCE.md); task conversations and the shared inbox are defined in [COMMUNICATION](COMMUNICATION.md). Reviewed reassignment after a hierarchy move, recurring work, advanced analytics, richer attachment formats and external notification delivery remain separate work. Qualification requirements are enforced at assignment and verified completion; this does not claim general calendar/availability matching. Mobile clients remain deferred. Production MFA, privacy/release and deployment gates remain in the overall roadmap.

Open task definitions can be amended under the [editing contract](WORK_EDITING.md): title, description, priority, meeting place/start, deadline and bounded capacity. Every edit requires a reason and preserves before/after history, notices, verified work and pinned reward terms. Coordinator and blocker changes use the explicit oversight commands; completion criteria may be configured only before the freeze conditions above. Activity verification accepts a manager's checked completion and text note; attachments follow the separate evidence contract. Local synthetic demo grants are installed explicitly with `npm run demo:work`, preserving all six accounts, passwords and existing data. No production grant bootstrap is implied.

## Validation

`npm run test:work` creates and drops a disposable database and checks scoped commands, delegation accounting, concurrency, lifecycle, retries, Activity, notifications and audit failure/expiry. `npm run test:work -- --browser` additionally runs Chrome through the host web application against that isolated API. Full repository checks, migration checksums and live smoke are recorded in `docs/STATUS.md`; this contract is not an audit or scale certification.
