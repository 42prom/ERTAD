# Reviewed position definitions

Positions describe permission bundles at one organizational unit. Creating or revising a definition uses the existing collective proposals, policy threshold, independent votes, receipts, notifications and transactional audit. It does not create a membership. Appointment or transfer to the approved definition uses the separate membership review.

`position.propose` plus `governance.propose` allows proposals; `position.approve` plus `governance.vote` allows review. Both also require unit visibility. These new capabilities are explicitly bootstrapped, never automatically granted by the migration and not delegable through this editor. Technical administration has no organizational override.

Every requested permission must be in the organizational allowlist and currently held by the proposer and each counted approving reviewer at the target. A unit-only grant cannot produce a subtree grant. Eligibility is frozen when submitted and rechecked at voting and after audit; losing authority cannot be compensated by a stale browser or an earlier vote. The current collective policy determines the threshold. There is no self-approval, arbitrary permission identifier or platform permission assignment.

Revision creates a fresh position ID and approved bundle. The previous position, grants and memberships are unchanged, and its approved version remains available for explicit appointment until separately retired. Use a distinct name for each revision so appointment selectors remain unambiguous. A predecessor has at most one successor. Its record version, unit and active state must still match when the change is approved. Subsequent revisions continue from the newest definition. Automatic rollout and batch member migration are not hidden side effects of editing.

Migration 41 adds explicit retirement through the same proposal and independent review. It accepts a position ID, current record version and displayed name, not a new permission bundle. `position.propose`/`position.approve`, the corresponding governance permission and unit visibility are required. Retirement grants no authority, so reviewers need not hold the old definition's delegated permissions. Existing membership and permission records are preserved. A retired definition remains visible in the scoped catalogue and history but cannot accept appointments or revisions; reactivation is not provided by this operation.

Active, scheduled and suspended memberships with an unexpired term block retirement, as do unexpired pending appointments/transfers and definition revisions. Historical ended/expired memberships do not block it. The catalogue exposes only a blocker boolean, not member identities. Resolve the membership or pending review separately, then submit retirement. Current source state, blockers and authority are checked at approval and again after audit; concurrent changes or an audit failure roll back the retirement, vote and receipt together. Stale requests can still receive rejecting votes or be withdrawn; a rejecting vote closes the request only when the configured collective threshold can no longer be met. There is no forced retirement or implicit reassignment.

The web catalogue supports scoped search, pagination, readable permissions and explicit unit/descendant scope. New/revised definitions require a reason, confirmation, session step-up and a 24-hour review window. The approvals page shows the proposed name and complete grants. An uncertain write retains its exact payload and idempotency key for retry. Stale or denied reads remove cached catalogue data.

SQL and HTTP checks use a disposable database. They cover scope, delegation ceilings, independent approval, retries, competing revisions/retirements, preservation of existing memberships, current authority and audit rollback. The retirement form requires a reason and explicit confirmation, retains an uncertain request for exact retry and disables submission when the displayed position version or authority becomes stale. Production identity/MFA and independent security acceptance remain release gates.

## Controlled adoption of an approved revision

Migration 43 connects the approved direct successor to the existing membership review journey. **Positions and permissions → revised position → Adopt revision / progress** shows added, removed and unchanged permission/scope pairs, bounded member search and each member's latest visible adoption request. Changing a permission from unit-only to descendants appears explicitly as removal of the old scope and addition of the new scope. Neither the definition nor membership is changed by opening this view.

Managers select at most 20 eligible memberships from the current 25-row page and confirm the displayed comparison. The browser submits a separate immutable request per selected membership. This is deliberately a series of independently reviewed requests, not an all-or-nothing bulk change. It reports confirmed submissions separately, stops at the first failure, retains the exact uncertain payload/key for retry, and never resends already confirmed entries. On a definitive conflict or denial it clears stale selection and reloads authoritative data. Navigation/reload does not provide durable storage for unsent choices; saved requests remain in Requests and the progress view.

Each request freezes the member row/version, original term/status, both ancestry paths and both definitions including exact grant/scope pairs. The displayed definition fingerprint is an optimistic concurrency marker, not an authorization credential. Membership proposal/approval permissions, member/unit visibility and the destination delegation ceiling are checked on the server. The requester and beneficiary cannot approve; the reviewer must currently hold every destination grant with sufficient scope. Technical authority confers none of these organizational permissions. Concurrent exact retries create and approve once.

Adoption is only to the direct approved successor in the same unit. Active or suspended memberships with an unexpired original term may be selected, including future-start memberships. Active task responsibilities, overlapping active/suspended destination memberships and another pending source change block a new request. Pending adoption also blocks retiring its destination definition. No task is silently handed over. Expired or ended memberships need a separate governed appointment and cannot be revived here.

Approval ends the old row and creates a distinct replacement preserving its original start, expiry (including no expiry) and active/suspended status. A future-start replacement remains scheduled; a suspended replacement remains without authority. Other memberships, assignments, Activity and contribution records are untouched. The old membership and immutable request retain the previous position and its history. This operation neither extends a term nor automatically adopts later successors.

Current source, definitions, bundles, actors, deadlines and responsibilities are checked again after transactional audit. Stale definitions or authority, duplicate destinations, audit failure and post-audit tampering roll back the member change, review and notifications together. The reviewer sees the frozen permission comparison; a stale request may still be rejected. See STATUS for executed tests and deployment state; scripts alone are not acceptance evidence.

## Catalogue and editor loading

Migration 44 keeps the existing catalogue authorization and post-audit checks, while allowing the web list to omit the editor's full delegation matrix (`includeGrants=false`). Position definitions still contain their approved grants; visible unit metadata and action capabilities remain scoped. The editor explicitly requests `includeGrants=true` when opened and when window focus returns. Missing or denied permissions disable submission while preserving entered fields, with an explicit retry for that read. The server still rechecks authority on every proposal and vote.

The original catalogue function disables PostgreSQL JIT for its own execution only. Neither database timeouts nor access controls are relaxed. This avoids repeated compilation and unnecessary permission-matrix work during normal browsing; it is not a scale benchmark. Callers omitting the optional flag retain the previous full-response contract.
