# Mobile security and technical control adaptation

The October 28 direction is to preserve the useful source application's mobile-management/security capabilities and adapt them to ERTAD's current console. The source working tree was inspected read-only; no source database, credentials or containers were used. Much of the implementation is already retained in ERTAD. This is an adaptation plan, not a claim that inactive source routes already protect the current application or that the inspection is a security audit.

The next priority is the technical control plane. It does not require finishing every remaining organizational feature first. Native/member mobile rollout still follows complete server contracts and the existing web-first priority: mobile serves group administrators and members, while council/regional and technical administration remain web-only.

## Delivery order

1. **Technical entry and separation:** completed read-only console plus the optional technical quick-login button. Its authentication still verifies a real password; it creates no grants. Existing six organizational accounts remain separate.
2. **Session-response journey:** migration 32 and the web console implement explicit web-session read/revoke capabilities, 25-row filtered cursor lists, password confirmation, bounded reasons, atomic audit/receipt writes and retry-safe termination. The affected client is denied on its next protected request; a new login is still possible. Current-session termination uses ordinary logout. Mobile credential/device revocation is not implied by this web implementation. See [session contract](PLATFORM.md#web-session-response).
3. **Security/provider policy:** migration 33 adds the [integration inventory and bounded diagnostics](INTEGRATIONS.md); inactive provider placeholders fail closed. Migration 34 connects [versioned web-session policy](SESSION_POLICY.md) to real login/refresh behavior, with independent technical approval and historical-value restoration through a new proposal. Actual identity-provider activation and credential-reference configuration remain incomplete and are deferred with mobile enrollment. Preserve the distinction between configured, reachable and verified integrations.
4. **Shield and monitoring:** the retained dashboard now provides [bounded API response observations](MONITORING.md), sanitized technical authentication history and navigation to separately authorized session response. Counters explicitly cover one running process and reset on restart. Country/IP response is now implemented through the separately approved network policy; durable alerts and multi-instance aggregation remain gated; retained risk-engine code is not evidence that an edge/WAF service is active in ERTAD.
5. **Mobile identity and device lifecycle:** bind enrollment/login to the actual ERTAD Android/iOS application, implement recovery/phone replacement and revocation using the approved identity contract, then expose a minimal technical device view. Reuse existing native integrity checks and test intent rather than inventing another framework. Version/compatibility controls may be added when the supported-release contract is defined; they were not verified as an existing source feature in this inspection.
6. **End-to-end acceptance:** test the ERTAD journeys on supported physical Android/iOS devices, including replay, stale/wrong-app evidence, provider outages, device replacement and revoked credentials. The user's report that the source application was device-tested is retained as baseline information, not represented as new ERTAD device evidence.

Existing work, decisions, membership and contribution lifecycle gaps remain in the V1 backlog. They do not justify repeatedly postponing technical control adaptation. Production identity/biometric retention, MFA, external audit checkpoints, recovery, monitoring and restoration gates still apply before release.

Use one API, one canonical database and the existing management application. Extend a working feature across its SQL, HTTP and interface boundaries before opening the next settings screen. Preserve the distinction between organization management, technical response, private identity access and member mobile actions. Single-session termination reduces access and is allowed by its explicit response capability; permission grants, identity disclosure and consequential security policy changes require their own approval contracts and cannot be smuggled through this action.

## Interface and privacy

Extend the current **System administration** visual family with focused views for sessions, security policy, integrations and bounded security telemetry as their actual API journeys become available. Reuse the retained form/table/filter/dialog primitives, Georgian/English translations and web themes. Do not add nonfunctional controls or show fictional device/security statistics.

Technical management must not reveal an organizational member directory, legal identity, biometric samples, private messages, ballot choices, raw push credentials or account passwords. Security response can invalidate a permitted credential/session without changing the person's organizational memberships, decisions, work or points. Membership authority remains the Organization/Governance modules' responsibility.

## Operator-selected mobile authentication (2026-11-05)

Accepted product direction, expanded to three profiles on 2026-11-05; implementation pending. The technical sidebar will expose **Mobile access → Registration and sign-in**. Its primary control has three mutually exclusive profiles. Hybrid is the recommended initial selection when this feature becomes available; this recommendation does not activate a runtime default.

| Mode | Member journey | Assurance recorded |
|---|---|---|
| Google account | Sign in with Google, then bind the ERTAD mobile credential to the device | Google-account authentication; document identity, age and person-level uniqueness are not established by this alone |
| Document and face verification | Supported document authenticity checks, liveness/PAD, face match and person-level uniqueness, followed by device binding | Only the identity evidence actually verified by the server; no success from a client flag or mock provider |
| Hybrid: browse first, verify before participation | Google authentication and device binding permit authorized reading; complete document-and-face identity proofing before the first vote or other protected domain write | Reuse the account's current verified identity if already established; otherwise record it only after successful proofing |

The chosen profile applies to mobile enrollment, establishing access on a new device and permitted actions. Hybrid intentionally combines two methods inside one profile: it is not an outage fallback or two competing active policies. A previously document-verified account can continue with its accepted bound credential in hybrid mode without being forced to create a Google account or repeat proofing. Normal return visits use the previously bound, revocable device credential under the current policy; they do not require a passport scan on every launch. Device-local biometric unlock is separate from remote document/face verification. The application shows the effective journey and any verification requirement, not a choice that bypasses policy. Web administrator authentication and development Quick Login are unaffected.

### Access matrix and one-time proofing

Keep four independent server-owned facts: the authenticated account, its identity-assurance status, the current device/session assurance, and current organizational permissions. A successful sign-in, a verified person or an attested device does not imply the other facts. The following matrix describes mobile policy ceilings, not new organizational grants:

| Action | Google profile | Document-and-face profile | Hybrid profile |
|---|---|---|---|
| Read content | Only content allowed by audience, membership and disclosure policy | Same, after required enrollment | Same after Google access or an existing accepted verified credential |
| Submit a poll/survey/referendum/election response | Account-level advisory participation only when its published eligibility permits it; never represent this as verified-person voting | Valid identity proof plus current session, permission and electorate eligibility | Denied before valid identity proof; after proof, use the same eligibility checks as the document profile |
| Other domain writes, including task participation, messages and management | Explicit domain permissions and assurance floors apply | Explicit domain permissions and assurance floors apply | Read-only before valid identity proof; after proof, explicit domain permissions and assurance floors apply |
| Security and account maintenance | Own sign-out, device response, privacy requests and permitted recovery remain available | Same | Same; starting verification is allowed while domain writes are denied |

An unassigned Google account can see only content explicitly available to that audience, not private group messages, a member directory, protected tasks or results. Until such an audience/content policy exists, show onboarding and an empty authorized-content view instead of exposing organizational data. Google authentication and a referral code do not create membership. Age handling remains a separate pre-release requirement; an email claim is not age evidence.

In hybrid mode the first protected participation attempt shows **Verify identity to participate**, explains what will be checked and returns to the original item after verification. The user may also start verification from their account. Proofing failure, cancellation or an outage preserves permitted read access without enabling writes. After success, refresh server eligibility and require an explicit submission: verification must never automatically cast a vote or replay a pending business action. Show a clear result if the item closed or access changed in the meantime.

"One-time" means successful initial identity proofing is reused while it remains valid, including across polls and surveys. It is not permanent unconditional trust. Store minimal verified status, method/version, timestamps and validity/revocation metadata against the canonical identity; keep document/biometric evidence in its separately protected, retention-controlled boundary. Do not retain raw face media indefinitely just to remember completion. Initial proofing includes authentic document evidence, PAD/face match, applicable age checks and person-level deduplication. A selfie without an authoritative reference or the phone's local Face ID success cannot establish this status.

An existing account with valid document-and-face proof skips initial proofing regardless of whether its current accepted sign-in used Google or a device credential. Linking Google requires proof of control of the existing account and the new Google identity. If another account already owns the verified person identity, stop activation and use controlled linking/recovery; never create another voting identity or silently merge by email. Concurrent proofing/linking must enforce the same canonical identity, not two successful duplicates.

Every protected action still checks current policy, identity validity, membership/scope, device/session state, item lifecycle and duplicate participation at the server boundary. Changing devices requires secure device enrollment/recovery, not automatically another passport scan; lost/compromised credentials, revoked identity evidence or a documented risk trigger can require renewed proof. A past identity check does not count as a fresh authentication factor on later votes. If additional authentication is required, use an action-bound authenticator challenge with intent, not a reusable face-success flag. This separation follows the distinction between identity proofing and ongoing authentication; see [NIST's biometric authentication guidance](https://pages.nist.gov/800-63-4/sp800-63b.html#use-of-biometrics). No NIST conformance level is claimed.

All Decisions formats use the shared verification gate in hybrid mode, including survey submissions, so a format change cannot bypass it. Proofing does not expand a published electorate or create a second submission. The mobile publication contract must explicitly define whether already snapshotted but unverified members may finish proofing before the deadline, how this affects eligibility and the frozen quorum denominator, and how duplicate person identities are handled. Do not silently recalculate a denominator or claim real-person quorum from unverified Google-account counts. Binding/anonymous voting stays gated until its stronger eligibility and privacy contracts are implemented. Identity proofing services and telemetry must never receive ballot choices; future anonymous participation must preserve an unlinkable authorization/ballot boundary rather than attaching verification IDs to ballots or correlation logs.

### Technical operator workflow

Reuse the current versioned technical-policy proposal/review/audit pattern, with explicit mobile-policy read/propose/approve capabilities. An organizational administrator receives no technical authority from their title. The editor shows the effective profile, proposed profile, the read/write/verification matrix, prerequisite readiness, affected-account counts without identities, transition deadline, approval state and sanitized change history. Provider configuration and secrets remain separately controlled; a selector cannot manufacture an installed or verified provider. Prefer these three bounded presets over independent switches that can disable authentication, proof validation or audit. Technical policy can impose an assurance floor but cannot lower a published Decision's eligibility, grant organizational privileges or change its electorate.

An operator chooses a mode and an effective transition plan, previews its consequences, provides a reason and fresh authentication, and submits for independent technical approval. Production uses the required MFA; local development retains its password-only policy. Approval rechecks current capabilities, policy version, provider readiness and the recovery plan. Version conflicts, withdrawn grants, missing configuration and unavailable providers fail closed. Uncertain writes retain their exact request key and cannot silently submit a different policy. Historical restoration is a new reviewed version.

### Shared protections and identity continuity

All three profiles retain server-owned device binding, action-bound challenges, replay protection, applicable app/device attestation, session revocation, rate limits and current membership/scope checks. Provider failure never triggers automatic profile switching or a lower assurance requirement. Neither authentication method grants membership, points or administrator authority. Technical operators cannot browse identity documents or face samples through this panel.

Google identities are keyed by validated issuer and stable subject, never by email alone. Account linking requires authenticated proof of the existing account and the new method; matching email, a referral code or an operator action is insufficient. Invalid issuer/audience, expired or replayed proof, wrong application/device and a policy switch during a pending flow must be rejected. See [Google's OpenID Connect contract](https://developers.google.com/identity/openid-connect/openid-connect).

Existing ERTAD member IDs, memberships, work and points survive a mode change. Before activation, the transition contract must identify accounts lacking the new method, provide a bounded authenticated linking path, define any grace period and handle lost-device recovery without easier proof. Transitional old-method credentials can authorize only the explicitly bounded migration journey, not new enrollment or ordinary access under the obsolete mode. Pending login challenges are version-bound; session refresh and protected requests enforce the effective version. A normal change cannot strand accounts without a tested transition path; emergency suspension/revocation remains a separate response action. Restoration cannot revive a revoked credential or falsely upgrade assurance.

Google mode explicitly extends the previous document-only enrollment design. It is a legitimate alternative for account access, but cannot be labelled verified real-person identity. Existing operations requiring verified identity or person uniqueness continue to require that evidence; the mode change cannot silently remove their eligibility requirements. The exact mobile eligibility matrix, age handling and cross-mode duplicate-account handling must be settled and tested before enabling Google enrollment. Document evidence already established on an account is neither erased nor fabricated by switching modes.

1. Define the mobile account/device, assurance, eligibility and transition contracts, including recovery and retention. Keep existing web-account work first.
2. Implement the two authentication/proofing adapters and all three access profiles behind the same policy and device/session contract; reuse retained document/native adapters. Keep identity proofing status separate from session strength. Do not expose an operational selector before the server consumers exist.
3. Add the technical policy API, reviewed persistence and working panel; verify scope isolation, independent approval, concurrent/stale changes, audit rollback, secret redaction and no fallback on provider failure.
4. Connect Android/iOS journeys; test all six directed transitions among the three profiles, current/new/lost devices, linking conflicts, expired grace periods, old session denial and preservation of membership/work/points on supported physical devices.
5. Test hybrid API enforcement independently of button visibility: all domain writes denied before proof, scoped reading preserved, proof reused across Decisions, already verified users not re-enrolled, duplicate-account/concurrent linking denied, no automatic vote after proof, deadline/permission/revocation races rejected, no ballot data in provider/audit payloads, and no write upgrade during provider outages. Cover both languages/themes and accessible cancel/retry/false-reject recovery journeys with synthetic identity data only.

No Google credentials, external calls, mobile database migration or active security-policy change is introduced by this design update. None of these profiles has new ERTAD runtime/device acceptance evidence yet.
