# Reviewed membership lifecycle

Migration 39 extends the existing Organization membership and Governance review journey. It adds no person deletion, account suspension, new approval table or new permission grant. **Members → member card → Manage membership** acts on one specific membership/position. A person may retain other memberships and the authority they confer.

## Authority and state

The proposer needs `membership.propose`, `member.read` and `unit.read` at the source and destination. A different reviewer needs `membership.approve`, `member.read` and `unit.read` at both. Neither the requester nor the subject may decide; a subject cannot propose changes to their own membership. Regional authority can manage positions within its scope. Cross-region transfers require authority covering both regions, typically the council; two unrelated regional permissions are not implicitly combined across different actors. Technical administration grants confer no organizational authority.

`transfer` ends the selected source membership and inserts a new membership for the same member ID and an existing approved destination position. It can also change position within one unit. The destination must differ from the old position; an overlapping active destination membership blocks approval. Its finite expiry must be later than the request deadline, within 365 days, and no later than the source expiry when one exists. Transfer is not an implicit renewal or permission-bundle edit.

`revoke` ends only the selected membership. It creates no replacement, deletes no person and does not suspend the web account or unrelated memberships. Subsequent authorization reads immediately exclude the ended membership; unrelated authority remains independently valid. Reinstatement of an ended membership requires a new governed appointment. Migration 42 also allows ending an unexpired, currently effective suspended membership, under the same responsibility and independent-review checks. Expired/ended memberships cannot be revived by these operations.

Requests remain immutable in `membership_reviews`, alongside existing `grant` requests. The form uses a 24-hour decision window; the API permits at most seven days. Source record/version and both ancestry paths are frozen. Versioning detects a source record changed away and back. Request keys bind to kind, source/version, destination, expiry and reason; conflicting reuse fails. Identical concurrent approval retries apply once. The membership mutation, review closure, notifications and audit share one transaction.

## Suspension and resumption

Migration 42 adds `suspend` and `resume` to the same reviewed change route. There are no new tables, role-name checks, permission grants or automatic assignments. Both require the existing proposal/approval permissions and current member/unit visibility, a different reviewer and a subject who is neither proposer nor approver. This is organizational membership administration, not an emergency account/session lockout.

Suspension changes only the selected row from active to suspended. Its authority is excluded by the existing current-membership policy after approval; unrelated memberships remain effective. Resumption changes the same row back to active only while its original term is unexpired, its member is active, its original position/bundle remains approved and no other active membership overlaps that position. The original start time, expiry, position and bundle version never change. Scheduled memberships may be suspended/resumed, but resumption does not make them effective before their original start. There is no automatic timed restoration.

Suspension and resumption preserve active assignments instead of silently abandoning or moving them. Task responsibilities do not block a reviewed authority restriction. Managers must resolve those assignments through existing Work controls; suspension is not evidence of completed work and awards no points. Transfer and termination retain their responsibility blockers. Historical Activity and contribution records remain unchanged, with current-scope disclosure still enforced.

Source snapshot/version, ancestry, term, original bundle and current actor authority are rechecked after audit. Definition retirement, conflicting active membership, source/term tampering or authority loss rolls back the approval and notifications. A stale request can be rejected without changing membership. Retrying a request returns the same request ID and its current status, rather than creating a second change.

Current session, requester/reviewer authority, deadlines, source record, destination bundle and ancestry are rechecked after audit. New private SQL helpers and the retained grant implementation are not executable by the runtime role. Runtime cannot write membership/review tables directly. A rejected request changes no membership and may be rejected after target/dependency drift, provided the request and reviewer authority remain valid.

## Responsibilities, points and history

Applied, reserved, assigned, in-progress and submitted task participation beneath the source unit blocks transfer and termination proposals and approvals. The UI discloses only that responsibilities exist, not hidden task details. Finish or resolve participation through the existing task workflow first; no task is silently moved or reassigned. This conservative check applies even when another membership might retain access. Suspension and resumption preserve those assignments and do not use this blocker. Automatic handover is separate work.

Completed assignments, Activity, contribution entries, votes and member identity are neither reassigned nor deleted. Historical membership rows remain visible through existing scoped directory filters. Preserving earned points does not widen their visibility: **Points in visible scope** still uses current scope, so a displayed total can change after a transfer without ledger entries being removed. Private voting history is not exposed by the change review.

## Web workflow and validation

The server supplies per-membership action visibility and current destination choices. The form requires a reason, explicit intent bound to the displayed membership version and normal password confirmation; existing development quick-login step-up remains available only to configured fixtures. Refreshing to a changed version requires fresh confirmation. Suspension/restoration offers no replacement-position or new-expiry field. Uncertain submissions retain the exact payload/key in page memory and disable edits; nothing is claimed successful until the server confirms. Reload/navigation is not durable draft storage.

Existing `/reviews` pending/mine/history views show transfer, termination, suspension or resumption with the original unit/position and destination. Suspension/resumption detail also shows the unchanged original expiry. The unified inbox uses the same current two-scope visibility policy. Reading a notification does not approve it. A beneficiary who loses the required scope cannot use old notifications to recover organizational data.

`npm run test:members:lifecycle` uses a disposable database and actual SQL/HTTP boundaries, including suspension/restoration. `npm run test:members:lifecycle:browser` adds Chrome transfer, independent approval, termination and history checks through local Vite. `npm run test:members:suspension:browser` adds suspension, another account's approval, discovery under Suspended, restoration and independent approval; database assertions preserve the original term and active assignment. Existing review, inbox, directory and platform regressions remain required. See STATUS for executed evidence rather than inferring acceptance from test-file presence.

Migration 43 adds `revision` requests for controlled adoption of a direct approved position successor. Unlike ordinary transfer, these preserve the original start, expiry (including no expiry) and suspended status in a distinct replacement membership while retaining the ended source row. The position catalogue supplies bounded selection, frozen permission comparison and per-member request progress; each member still needs separate independent approval. Existing Work responsibility blockers apply. See [approved position adoption](POSITIONS.md#controlled-adoption-of-an-approved-revision) for exact authority, retry and partial-submission behavior. `npm run test:positions:rollout:browser` verifies this journey with two administrators.

Remaining: coordinated cross-unit transfers, safe automatic task handover, web-account lifecycle and production identity/MFA acceptance. No production deployment or account migration is included.
