# Shared task materials

Migration 24 adds a bounded list of named HTTP(S) links to existing Work items. The task detail page has **Task materials → Manage links** for current scoped managers. Readers see the current links; editing is available only while the task is open or offered. Use this for shared instructions, meeting information or supporting resources. Private completion reports remain a separate capability with their existing author/reviewer disclosure policy.

Up to ten links are stored in the task row, with a 120-character title and 2048-character URL. The API parses URLs and rejects unsupported schemes, credentials, control characters, whitespace and backslashes. Database validation independently restricts structure, size and schemes. Links are rendered as text anchors, never HTML, embeds or automatic previews. Opening an external destination uses a separate tab without an opener or referrer. ERTAD does not fetch, inspect, host or confer its access controls on external destinations; a destination may redirect after the user opens it.

Current session/step-up, active organization, frozen task ancestry and explicit read/create scope govern edits. Detail reads recheck scope after required audit. Writes use the existing organization/advisory locks, optimistic task version, idempotency receipt, audit transaction and final authorization check. Stale edits and changed-payload retries conflict. An exact committed retry returns its prior receipt even after task closure, provided current authority still holds. Failed audit rolls back links, version, event, notification and receipt together.

Work and membership-review commands can retry a PostgreSQL-declared deadlock victim at most twice after rollback, rerunning the entire database-only callback including authority and audit. Access failures, business conflicts and uncertain connection/commit errors are not retried. Storage callbacks do not use this helper. This is bounded recovery for concurrent requests, not a throughput or deadlock-free guarantee.

Replacement/removal changes the current list. History and audit record only the material-change action and identifiers; retry receipts retain a payload digest rather than removed URLs or query parameters. Links do not appear in task list projections or notice previews. Scoped existing Work notifications tell managers/affected participants about the updated task. Reads use no-store responses. Link updates never change assignments, completion, Activity or contribution points.

Delegated tasks do not automatically copy parent materials; their manager explicitly chooses appropriate shared instructions. Parent access is not implied by access to a child. Private files, identity documents and secret-bearing URLs must not be treated as public/shared instructions. Database backups retain their normal operational retention policy even after a current link is removed.

## Shared photos and PDF documents

Migration 25 extends the existing private reservation table with a material kind, media type and source digest. **Photos and documents** on task details accepts PNG/JPEG and PDF from current task managers on open/offered tasks. All current task readers may download; only current managers may remove. Private completion reports remain a separate kind and endpoint with unchanged narrower disclosure. Neither kind awards points or verifies work. No new port, service, table or bucket is introduced.

Uploads are raw bodies up to 5 MiB with matching MIME/signature checks. Original filenames are not persisted. A durable hidden pending reservation precedes processing; only the reconstructed output reaches private S3. Photos accept one frame and at most 16 million pixels, rotate to orientation, resize within 2400 pixels and become metadata-stripped PNG. PDF inputs allow up to five pages, each dimension at most 3000 points. Each page renders within 2000 pixels and is embedded into a new image-only PDF. Original scripts, attachments, forms, metadata and interactive links are not copied. Text selection, accessibility structure and digital signatures are lost; the UI states this conversion before upload. This is unsuitable for archival originals.

Parsing runs in a separate short-lived Node process with no application credentials, a 192 MiB JavaScript heap limit, 20-second timeout and bounded output. One converter runs per API process; competing requests receive retryable 503. Native allocations are not fully bounded by the JavaScript heap. This is process separation and content reconstruction, **not an OS sandbox, malware scan or security certification**. Source bytes are never written to shared storage or temporary files by the application. The parser uses [Sharp](https://sharp.pixelplumbing.com/api-constructor/) and [PDF.js](https://mozilla.github.io/pdf.js/api/draft/api.js.html), with [pdf-lib image embedding](https://pdf-lib.js.org/docs/api/classes/pdfdocument) for the new document. Dependencies and the worker asset are part of the backend build.

Reserve, publication, download and removal use current session, active organization, frozen task ancestry, explicit Work authority and transactional audit. Authority is checked again after storage/audit before bytes are released. Publication failure leaves a hidden, expiring reservation; an exact retry reuses its source digest/key and canonical bytes. Conflicting retries fail. Storage callbacks are never automatically retried as database-only work. Downloads check hash/size and use no-store, nosniff, restrictive CSP and generic attachment filenames. Lists omit uploader, hashes, storage keys and originals; no file content enters audit or notice previews. File changes currently require task refresh and do not create Work notices.

Pending rows expire after 15 minutes; ready files after 90 days from reservation. Lifetime quotas are ten reservations per manager/task and 25 per task, separate from report quotas. Removal immediately expires access without replenishing lifetime quotas. `npm run evidence:purge` deletes expired objects for both kinds and records minimal audit; physical deletion requires that operator command. Production still requires monitored scheduled cleanup, storage credential scoping/encryption and parser hardening review. Mobile files, arbitrary office formats, rich completion evidence and criterion-specific attachments remain deferred.

Run `npm run test:work-materials` for disposable-database/HTTP checks and `npm run test:work-materials:browser` for the isolated Chrome journey. The database cases also run in `npm run test:work`. Current results are recorded in [STATUS](../STATUS.md).

Run `npm run test:work-files` for converter, database, HTTP and private-storage checks, and `npm run test:work-files:browser` for manager/reader/sibling-region Chrome checks. `npm run test:work-evidence` verifies report separation and existing retention behavior.
