# Foundation decisions

## ADR-001 — Isolated repository and incremental reuse
Accepted: ERTAD has its own repository and data volumes. source application remains read-only reference with dirty changes preserved. Reuse reviewed framework/patterns/components incrementally; do not import national-election schema or production data. Initial user authorization covers a runnable local foundation; full domain implementation waits for its audit and security gates.

## ADR-002 — Host development, optional container apps
Accepted: API (13000) and Vite (15173) run locally with hot reload. Compose defaults to PostgreSQL (15432), Redis (16379) and S3 (19000). All bindings are loopback. Dedicated bridge network avoids sharing service DNS/volumes with other projects; outbound traffic is not blocked by this bridge. An internal-only Docker network was unsuitable for host access on this Docker Desktop setup. Optional `apps` profile supplies parity checks/CI. No Kubernetes, message broker or domain microservices.

## ADR-003 — Separate semantic visual families
Accepted: web follows reviewed source application sidebar/slate/sky conventions. Mobile retains a separate night family; provisional day design follows navy/blue direction. Shared semantic tokens generate CSS and Dart, while interaction semantics remain consistent. Theme/locale preferences work locally without a backend. Do not claim Flutter/device validation from a browser palette sample.

## ADR-004 — Production disabled until security gates
Accepted: product APIs deny access and startup in production/unknown modes fails. The original foundation gallery was replaced by the complete source application web baseline under ADR-011; its protected routes still require a server-confirmed session. Implement real identity, bootstrap/MFA, scoped permissions, data protection and release gates before enabling production. A non-production build is not authentication bypass.

## ADR-005 — Local S3 implementation
Accepted for local development: SeaweedFS single-node `mini`, separate volume, credentials and private initial attachment bucket. No real attachments or biometric data are loaded. Legacy MinIO registry pulls returned 401 and its official community repository is archived; it is not selected as a new dependency. Production storage/provider, retention, encryption, backups and independent audit-checkpoint destination remain separate reviewed choices. Sources checked 2026-10-01: [MinIO status](https://github.com/minio/minio), [SeaweedFS quickstart](https://github.com/seaweedfs/seaweedfs#quick-start).

## ADR-006 — Phased scope and privacy baseline
Accepted: V1 core, V1.5 network, V2 gamification. New profiles Private; no unauthorized membership enumeration; minimum anonymous electorate 10; rare-attribute threshold k>=10; external signed audit checkpoints mandatory. Adults-only product default pending concrete enrollment policy. Public discovery is constrained by organization and context. No XP/referral/money authority.

## ADR-007 — Local agent workspace stays private
Accepted: local prompts, agent instructions, skill copies and working audit reports are excluded from Git and Docker contexts. Hooks and CI scan eligible/tracked filenames to catch accidental forced additions. Checked-in code, tests, README, ADRs and operational architecture are independent of private working instructions. This guard is not a complete content/secret scanner; content review remains required.

Runtime sources checked: [Node release lifecycle](https://nodejs.org/en/about/previous-releases), [Compose dependency health ordering](https://docs.docker.com/compose/how-tos/startup-order/). Lockfiles and pinned image digests define actual builds; sources do not substitute for runtime checks.

## ADR-008 — Actual imported application reuse with preserved local changes

Accepted for migration planning, 2026-10-01: source application's local working tree is the implementation source, including its uncommitted security improvements and tests. Preserve source revision and file hashes, transfer complete reviewed flows into ERTAD and retain isolated ERTAD infrastructure. The web target is at least 90% of applicable original journeys/structure, tracked with explicit exclusions rather than an unmeasured code-percentage claim. No imported source modification, whole-schema import, secrets or production-data transfer is implied. P1 migrates presentation; P4 connects authenticated flows after the Identity and Authorization gates. See the [transfer map and delivery sequence](MIGRATION.md).

## ADR-009 — Zero Trust is a migration acceptance requirement

Accepted design requirement, 2026-10-01: preserve native integrity adapters together with their server validators and regression tests. Every protected request independently requires valid session/assurance and applicable permission/scope. Client verification flags, network location, device attestation and administrator rank cannot substitute for authorization. Generalize action binding without creating a participant-to-ballot correlation path. Provider outages and unsupported devices must not create authentication bypasses; offline UI distinguishes unconfirmed state. This is not a claim that every current source application path already meets the target. See the [boundary and negative-test matrix](MIGRATION.md#zero-trust-contract).

## ADR-010 — Identity continuity reference has an explicit activation gate

Proposed, 2026-10-01: support new-device/recovery identity continuity with renewed document authenticity and PAD/face checks, stable verified-person matching and, if justified, a protected biometric reference. Reference format, provider/model, retention/deletion, key custody, matching and manual-review policy must be resolved before storage is enabled. No indefinite raw media retention, biometric-only account takeover path or automatic replacement on mismatch. Routine same-device login and re-proofing have separate contracts. See the [recovery design](MIGRATION.md#identity-continuity-biometric-reference-and-recovery).

## ADR-011 — Intact imported application transfer before subtraction

Accepted, 2026-10-02: use the complete local imported application as the active implementation baseline, including uncommitted tests/security changes. Transfer web, backend, Flutter/native and supporting service code first; then remove wallet/cryptocurrency/election machinery and adapt complete flows. This supersedes the component-first reconstruction sequence. Keep ERTAD Git history, host development, isolated data services, publication exclusions and production gates. Working reports, secrets, real data and unreviewed face/media examples are not application baseline inputs.

The full original web replaces the small gallery. Original backend source and migration history are retained without running the full application: `backend/src/index.ts` is ERTAD's restricted composition (health plus the opt-in local auth subset in ADR-012), `src/ertad-server.ts` retains the original server and rejects non-test startup, and the applied runner reads only `db/foundation`. Python services are source-only. The original mobile state/theme architecture is preserved at intake; conversion to target architecture and five destinations follows complete transfer. Mobile identifiers and default transport are isolated from source application, and release startup is blocked.

Temporary presence of old product code is not feature activation or acceptance of its authorization/privacy model. Existing source application role names, old decision protocol and biometric policy still require ERTAD-specific replacement. The full source is traceable in the [source manifest](source-manifest.json); runtime and test evidence belongs in [STATUS](../STATUS.md).

## ADR-012 — Local web login uses the adapted source application security primitives

Local MFA behavior below was superseded by ADR-013 on 2026-10-03. Password/session/CSRF/audit protections remain active.

Accepted, 2026-10-02: enable local access through source application's existing password/MFA, session, CSRF and audit implementation. A local CLI generates independent random credentials on an empty administrator table, stores them in ignored files and enables the host runner's opt-in authentication composition. Existing accounts are preserved. Only the minimal administrator/session/audit schema is applied; no source application domain schema, identities or administrator credentials are imported.

MFA codes are consumed atomically per account, concurrent `/me` calls retain the same protected CSRF token, session creation and successful-login audit are transactional, and runtime grants cannot create/elevate accounts. Unsafe requests require the configured local web origin, sessions have idle/absolute/concurrency limits and logout revokes them. A disposable PostgreSQL suite exercises the negative boundaries and audit failure. A real local browser login/reload/logout is also verified without recording credentials in traces.

The legacy `superadmin` label supplies menu visibility only. Every product operation remains unavailable even after login; tenant authority and production administrator enrollment remain separate gates. Production startup is disabled. Optional application containers keep this local-access feature off by default. This development account is not a permanent production root, a member identity, or evidence that full Zero Trust/biometric/governance requirements are implemented.

## ADR-013 — Password-only development access and ERTAD identity

Accepted, 2026-10-03: local development login and step-up use the existing password without an authenticator code, as requested. Only the development/test composition can select this policy. Password verification, lockout, server sessions, Origin/CSRF, audit and production rejection remain enforced. The strict router defaults to mandatory MFA and retains replay tests. MFA for every web user is a prerequisite for enabling production, including enrollment and recovery workflows.

All active product branding, identifiers, filenames, service defaults and documentation now use ERTAD. Browser events, cryptographic domain separators and matching mobile/server tests were changed together. Native identity is `ge.ertad.mobile`, Dart package is `ertad_mobile`, and platform icons are generated from the ERTAD mark. Old protocol tokens/credentials are not compatible and were never imported. Full historical source paths/hashes remain in ignored provenance records; the public manifest uses opaque source entry numbers and current target paths.

Application ports are 13000/15173 both on the host and inside optional application containers. Host PostgreSQL/Redis/S3 ports remain 15432/16379/19000; their standard internal engine ports are unchanged. Optional inactive biometric/Shield code defaults to 18000/18080. No original source service is reconfigured or stopped.

One existing local migration contained the inherited name only in its leading comment. Its comment was renamed, executable SQL was compared unchanged, and the exact previous checksum was verified before updating the local migration record transactionally with an audit event. No schema/data transformation or general checksum bypass was introduced; clean databases apply the same executable SQL. This is a local pre-release metadata correction, not a production migration procedure.

## ADR-014 — Remove cryptocurrency and replace the decision protocol in place

Accepted direction, 2026-10-03; implementation pending: remove cryptocurrency, wallets, transfers, token rewards and chain infrastructure from the ERTAD copy. Replace the imported election protocol with a Decisions module in the existing API and PostgreSQL. Preserve applicable web/mobile journeys, enrollment adapters and security controls, adapting their contracts rather than building a second application. The [subtraction batches and acceptance cases](MIGRATION.md#subtraction-and-adaptation-batches) define completion; disabled code alone does not count as removal.

One decision lifecycle supports polls, elections, approvals and binding votes. Organization/unit scope, eligibility at opening, options/candidates, deadlines, quorum, tie handling and result visibility are explicit policy. The initial rule is one eligible member per vote, with results unavailable until closure. No financial contribution can increase voting authority. A binding outcome must still pass the authorization/independent-approval rules of any operation it requests; a poll is not a permission grant.

Anonymous mode remains supported. Separate participant records from randomly identified ballots; neither schema nor application metadata may supply a participant-to-choice link. Coarse times, restricted results and the minimum electorate of ten are required, including suppression of unanimous or revealing breakdowns. Reuse the original authoring, active/history and question components while replacing receipt/chain/proof contracts. Preserve standard cryptography for authentication, encrypted secrets, device evidence and independently signed audit checkpoints.

Recommended initial anonymous submission contract, to be verified before activation: immutable first accepted vote; transactional unique participation and ballot insertion; concurrent/duplicate attempts cannot add another ballot. After an ambiguous network response, the client queries participation status and reports only that participation was recorded. It must not claim which choice was stored. Do not store user-bound choice fingerprints, ballot IDs or cached receipt bodies to implement retries. Re-voting and stronger receipt guarantees require a separately reviewed unlinkable design. Ordinary non-anonymous mutations retain payload-bound idempotency.

This simple model protects application-level disclosure and stored application records; it is not end-to-end verifiable voting or a promise of anonymity against a compromised server, privileged database transaction-log access or network observation. The submission handler processes identity and choice in memory. Database transaction metadata can correlate writes even without a foreign key. Document these limits before enabling anonymous decisions; application logs, traces, exports and analytics must not introduce easier links. A stronger threat model requires a new design review, not a claim that random IDs alone solve it.

No inherited domain schema is applied to accomplish subtraction. Keep rollback provenance outside publishable product files; remove unexecuted legacy schema with its final consumers. Existing applied foundation migrations retain their checksums. New domain migrations ship with their tested slice. Authentication/organization/permission boundaries precede enabling decisions; incomplete pages never imply an available API. The detailed policy, SQL and new test results remain pending.

## ADR-015 — Deliver complete journeys with small shared domain primitives

Selected plan, 2026-10-03; domain implementation pending. Keep one modular API and one canonical PostgreSQL database. Extract imported behavior when a journey needs a new boundary; do not relocate every file or replace every working client dependency first. Modules own writes to their tables and expose explicit operations/projections. Cross-module work that must succeed together shares a database transaction through those operations. Redis remains temporary infrastructure; the biometric provider boundary stays isolated.

Reuse WorkItem/Assignment for different kinds of work, Channel/Message for communication audiences, and Decision for voting variants. Add schema-validated, versioned declarative definitions only for actual variation needed by a feature. Keep important relationships and constraints typed and explicit. No universal executable workflow language, catch-all entity table or generic CRUD framework. Governance Approval remains an independent authorization control for sensitive actions; a Decision of type APPROVAL cannot bypass it. Ordinary task creation does not automatically need multi-person approval.

Centralize session assurance, permission/scope policy and disclosure projections; enforce them in domain operations reached by HTTP routes or workers. Resource organization and current authority come from server state. Permissions/approvals are revalidated when the protected mutation executes, with concurrency controls appropriate to the change. UI capabilities aid navigation but grant nothing. Each accepted endpoint has one versioned request/response contract exercised by server and client tests. Sensitive operations write minimal audit records atomically with the domain change; audit, Activity and notification delivery remain distinct records with distinct privacy/retention rules.

The first delivery-dependent feature persists a minimal delivery record in the same transaction as its domain change and retries delivery with deduplication. Reuse NotificationDelivery for that purpose; add no general event bus or separate queue service in advance. Domain success does not depend on a push provider being available. Restrict stored delivery payloads and recheck current access before sending; never put anonymous ballot IDs, choices or actor-to-choice links into delivery, audit or generic retry records. Crash/retry tests must not claim exactly-once external delivery without provider support.

Build one full member/task/verification/Activity journey before expanding the product breadth. Add required authorization, audit and minimum qualification rules with it; do not postpone these until all screens exist. Introduce the target Flutter state/transport/navigation wiring feature by feature where it helps that journey, preserving tested capture/native adapters and avoiding duplicate long-lived API clients. Adopt shared presentation primitives in affected screens rather than rebuilding a parallel gallery. See the [execution checkpoints](MIGRATION.md#execution-checkpoints); the complete V1 scope and release gates remain required.

## ADR-016 — Contribution points in V1

Accepted scope, 2026-10-05; implementation pending. V1 Activity includes non-monetary contribution points for confirmed voting, survey and activity participation, plus scoped custom recognition by authorized higher-level managers. The super administrator configures versioned rules, amounts and delegation limits through explicit permissions. This extends the earlier V1 scope; it does not restore cryptocurrency/payout infrastructure or require V2 levels/leaderboards. Financial contribution records remain separate.

Reuse the Activity ledger, canonical source events, Governance Approval where policy requires it, strict audit and existing web/mobile history components. Issue once per eligible source/category even across rule versions; enforce concurrent caps; correct through compensating records. No self-award, role-name bypass or points-based authority. Anonymous awards depend on participation only and must not carry ballot/answer links or finer timing/correlation metadata. See [Contribution points](CONTRIBUTION.md) for lifecycle, privacy, delivery order and acceptance cases. Add real storage and APIs with the first verified Activity journey, then manual awards and Decisions participation; no placeholder reward service now.

## ADR-017 — Web-first development and isolated demo identities

Accepted 2026-10-07: prioritize the web management journeys. Council/super administrators and regional administrators use web; the later mobile audience is group administrators and members. Regional/council administration and authority must not be issued to mobile sessions. Mobile enrollment, native integration and device qualification remain deferred work, while current web authorization, privacy and audit requirements stay enforced. This changes delivery order, not production identity assurance.

The explicitly enabled loopback development demo creates one synthetic organization, two regions, their two groups, two council accounts and two accounts per region. An offline owner script provisions bounded persisted memberships and two initial review fixtures with an audit event. It neither changes the existing local administrator nor impersonates verified real-person enrollment or production bootstrap. Re-running preserves passwords, grants and review outcomes; mismatched fixture state fails rather than resetting data.

Quick login is an intentional local development convenience limited to these six fixture accounts. The server retains random passwords in an ignored file and passes them through the existing password/session/lockout/audit handler; it does not expose passwords to the browser or accept arbitrary account/role claims. Demo step-up remains tied to the currently authenticated fixture account and requires Origin and CSRF. Listener/peer/Host/Origin checks and an explicit feature flag constrain exposure; production startup rejects this composition. Any local process able to use this enabled loopback demo can sign into its synthetic accounts, so these identities must never hold real organization authority or real data.

The workspace and review inbox use server-scoped context/count/detail queries. Regional pairs see their own subtrees; council accounts have explicit root-subtree memberships. The requester and beneficiary cannot decide their own request. The demo's scoped identity labels are fixture projections only and do not implement a general member directory. Existing unfinished pages remain in source while navigation exposes the currently accepted workspace and review journey. No new schema or app container is required. See [web demo operations](../OPERATIONS.md#local-web-demo).

## ADR-021 - Universal multi-admin threshold consensus and notification engine

Selected 2026-10-14 for collective administrative governance. Unilateral administrator actions present an unacceptable concentration of authority and operational risk. Deliver a universal, unit-scoped multi-admin consensus engine for actions that require collective agreement across Council, Regional, or Group administrators.

The consensus engine applies strictly to administrative actors within an organizational unit and never replaces private member voting. It provides:
1. **Universal Action Dispatcher**: One immutable proposal ledger (`governance_proposals`) and vote record (`governance_proposal_votes`) that encapsulates typed actions across domains:
   - Directives: Council and regional administrative directives and operational policy updates.
   - High-impact Tasks & Funding: Authorizing sensitive/high-budget work items and releasing financial accounting (ADR-020).
   - Contribution Points: Granting custom non-monetary participation points, corrections, and manual awards (ADR-016).
   - High-level Decisions: Authorizing binding or structural polls, referendums, and electorate boundaries.
   - Position & Authority Lifecycle: Unit-level appointments, position modifications, and sensitive permission grants.
2. **Threshold & Quorum Rules**: Explicit, verifiable consensus criteria calculated against current active administrators within the proposal's unit:
   - Simple Majority (50% + 1 of active unit administrators)
   - Supermajority (2/3 of active unit administrators)
   - Unanimity (100% of active unit administrators)
   - Fixed count (minimum N independent approvers)
3. **Full Administrative Transparency**: Unlike anonymous member ballots, all administrative proposals and votes are fully transparent and accountable. The initiator, all voters, their decisions (Approve/Reject), timestamps, and mandatory written justifications are recorded and visible to all authorized administrators of that unit.
4. **Targeted Notifications & Actionable Review**:
   - Creating a proposal atomically dispatches targeted in-app notifications directly to every eligible administrator in that unit's scope whose decision is required.
   - The review inbox/card presents direct, actionable **Approve** and **Reject** buttons, visual quorum progress (e.g., "2 of 3 approved"), and requires an explicit decision reason and fresh step-up authentication.
5. **Atomic Transactional Execution**: When the final threshold-satisfying vote is cast, the proposal status becomes `APPROVED` and the underlying domain mutation executes within the exact same database transaction, accompanied by an immutable audit event. If threshold is not met before the deadline, the proposal expires and no mutation occurs.

Implementation clarification (2026-10-18): migrations 13–14 use the concrete `collective_proposals`/`collective_votes` contract for directives, policy, funding and recognition. The eligible cohort is frozen at proposal creation and includes only current, explicitly authorized administrators with membership in that unit, excluding the proposer and beneficiary. Majority/two-thirds/unanimity use this **independent reviewer cohort**, rather than counting excluded authors as implicit votes. Current authority and ancestry are checked again on each decision and after audit; revocation never reduces the frozen threshold. Fixed one independent approval is the initial policy, supporting the two-admin local fixtures; policy changes themselves require approval under the previous rule. High-impact task authoring, binding Decision authoring and existing appointment/unit reviews are not yet routed through this dispatcher; their existing independent controls remain intact. External notification delivery and a merged cross-domain inbox remain separate work.

## ADR-022 - Separate organizational discovery from technical platform administration

Accepted 2026-10-28. Organization managers need scoped member discovery, membership states and permitted contribution/participation views. Migration 30 gives discovery its own `member.read` permission with `unit.read`, while existing source permissions continue to govern points and Work. Shared organizational names are separate from private identity/account data. Navigation into appointment/recognition flows confers no authority and submits no mutation.

Platform technical administration is a separate planned authority scope in the same web application. Reuse retained security/audit, integration/settings and session tools only after adapting their API authorization, minimal disclosure and configuration invariants. A technical account must not gain organization membership, membership/points management, ballot access or impersonation through its role label or technical settings. Organizational council positions do not automatically receive platform configuration authority. Sensitive technical changes require step-up, reason, audit and independent approval where the change policy requires it; mandatory authorization/audit invariants cannot be toggled off. This application boundary is not a claim that a database/server owner is technically unable to alter the deployment.

Sequence: complete member discovery first, then explicit technical-account capabilities and a read-only system/security view, followed by scoped session response and reviewed integration/configuration mutations. The technical account and panels are not activated by migration 30. Preserve existing development quick login, source reference isolation and production release gates.

October 28 implementation: migration 31 and the explicit local installer activate the read-only [technical console](PLATFORM.md). One technical classification row carries bounded permissions and expiry; bidirectional serialized checks prevent combining it with organizational membership. The existing session/audit primitives and console components are reused. Only dependency readiness, own-session count and an allowlisted payload-free technical journal are disclosed. Sensitive mutations, production enrollment and comprehensive security telemetry are separate work.

## ADR-023 - Operator-selected mobile authentication

Accepted product direction 2026-11-05, expanded the same day; implementation pending. Mobile members and group administrators will use one effective access profile selected from the technical console: Google account authentication, document authenticity plus liveness/face verification, or hybrid Google browsing with verified identity required before participation. Hybrid is the recommended initial profile, not an activated runtime default. This extends the earlier document-only enrollment design. Web administrator login, local Quick Login and web-first delivery priority are unchanged.

Reuse the existing technical policy/version/review/audit mechanism. Explicit technical capabilities govern selection; an organizational title grants no configuration authority. All profiles share ERTAD device binding, server-side Zero Trust checks, revocable sessions and existing organizational authorization. Google account authentication is not evidence of document identity, adulthood or one-real-person uniqueness. Store actual assurance independently of the selected profile and preserve eligibility checks that require stronger identity evidence.

Hybrid permits only authorized reading before identity proofing, with account/security maintenance and verification available. Initial document/PAD/face/uniqueness proof is reused while valid; an already verified account is not re-enrolled at each poll or when it uses a linked Google account. Authentication freshness, current device/session assurance and domain eligibility remain checked on every protected action. A completed proofing flow never automatically submits a vote. Google-only advisory participation must be labelled account-based, not verified-person voting. Technical configuration cannot relax a published Decision's eligibility or expose private content. Mobile electorate/quorum, age, recovery and anonymous-ballot boundaries remain explicit implementation gates.

A mode change must include a tested account-linking/recovery transition, with no email-based automatic merge, silent fallback or automatic authority grants. Existing member identity, work and contribution records remain stable. The detailed panel, transition and acceptance contract is in [Mobile control](MOBILE_CONTROL.md#operator-selected-mobile-authentication-2026-11-05). No runtime selector or mobile authentication adapter is activated by this decision.
