# Communication: administrative inbox and private channels

The first Communication journey is `/inbox`: membership appointments, unit creation requests, tasks, collective administrative approvals and published Decisions in one permission-scoped queue. These are sources inside one inbox, not new business modules. Decisions, Work, Identity, Organization, Contribution and Governance retain their own lifecycle rules.

The global bell shows unread records. The page defaults to **Needs my action** and also supports **Unread**, **All**, category filters and 25-record pagination. Reading does not approve, accept, assign, verify or dismiss a business request. Opening an item navigates to its existing domain page and fetches the current detail with that module's authorization. Opaque navigation state is consumed once and is not placed in the URL. Non-sensitive filters can be bookmarked.

## Authority and disclosure

Migration 15 projects canonical domain records through their existing visibility functions. Current membership, permission, hierarchy ancestry and independent-review rules determine visibility and action labels. Collective financial and recognition records retain their additional disclosure permissions. No private reasons, donor details, amounts, qualifications evidence or member directory are copied into previews. The page is not a platform-wide activity feed: it includes requests relevant to the recipient, their actionable reviews and their existing task/collective notifications. An action label is a shortcut to the domain, never authorization to execute a transition.

The restricted application role can execute the validated inbox command but cannot read or write its tables or call internal projections directly. Session validation, organization locking, Origin/CSRF on acknowledgement and transactional audit are retained. Scope and session validity are evaluated again after audit persistence. Audit failure rolls back acknowledgement. Counts use the same visibility projection as rows.

## Read state

Work and collective approvals reuse their existing notification read state. Membership decisions synchronize with existing membership notifications. The two small new recipient tables record pending membership/unit request read versions; they do not duplicate the request payload or lifecycle. Each pending request is version 1 and its decision is version 2. An expired deadline changes its actionability without fabricating a new event/version.

Acknowledgement requires the observed record version. Repeating an old acknowledgement cannot consume a newer task event or approval decision. Acknowledgements are monotonic and idempotent; requesting a future version is rejected. A read item stays in the action queue until the domain action is resolved or authority/eligibility changes. Each original module can still acknowledge its own notifications. The browser refreshes on local workflow changes, window focus and every 60 seconds; it does not claim real-time delivery.

## Validation and remaining scope

`npm run test:inbox` uses a disposable database with all migrations and synthetic fixtures. It covers aggregation, sibling denial, summaries, independent review, read-version races, canonical read synchronization, audit rollback, session and permission expiry, HTTP/CSRF/Origin boundaries, hierarchy moves, expired requests and deterministic pagination. `npm run test:inbox:browser` additionally requires local Vite and Chrome; it checks exact-record navigation, read versus action, recipient scope, both languages/themes and four viewport widths. No production or source-application data is used.

This is not the complete Communication module. Private operational channels, task-linked conversations, temporary writing restrictions/appeals, moderation notices and Decision notices are described below. Direct messages, personal blocking, broader membership/platform bans, additional system message sources, scheduled advance reminders, external delivery/retries and secure attachments remain separate work. Native member delivery is deferred with the mobile application. Offset pagination may shift when the underlying workflow changes; this queue is not an immutable export or a measured scale benchmark.

## Published Decision notices

Migration 17 extends the existing inbox projection and command; it does not add a second delivery service or duplicate Decision payloads. Polls, referendums, surveys and elections use the same notice lifecycle. The new source is `decision`, with the **Polls and surveys** category. Unpublished drafts, including cancelled drafts, are excluded. Already-published records become visible through their current state when this migration is applied; no historical notification text is backfilled.

A notice requires current domain visibility, unchanged frozen ancestry and either current eligibility through the original frozen electorate membership or explicit scoped management/publication authority (or the still-authorized creator). A new or replacement membership does not silently enter an existing electorate. Vote-only group members can receive ancestor-wide Decisions without receiving a member directory, unit metadata or management powers. Moving a hierarchy branch hides the notice rather than forwarding it to newly related managers. These notices currently support explicitly named Decisions only; anonymous delivery needs its own privacy-reviewed contract before activation.

Only an eligible member who has not yet participated sees **Participate** in **Needs my action**. Reading never submits a vote or survey response. The original Decision page revalidates authorization and opens the exact record through transient navigation state, even when its status differs from the page's current list filter. IDs and private titles stay out of URLs. Existing form controls, confirmation and submission rules remain in force. Completion of participation refreshes the inbox and bell through the existing workflow event.

Notice versions are separate from draft-edit versions and ballots: publication is 1, elapsed deadline is 2, explicit closure is 3, and cancellation is 4. The deadline state is evaluated when the inbox is queried; this is not a background scheduler, advance reminder or external push. Expired/closed notices are informational and open the original results view; expiry does not fabricate an extra approval obligation. Exact-version, monotonic acknowledgement leaves later lifecycle updates unread. Votes and other people's answers do not increment notice versions or reveal participation in another recipient's queue.

One recipient read-state table references the canonical Decision. No answers, choice options, result totals, profile fields or voter identifiers are copied into its inbox preview, read state or audit payload. Read-state changes share the existing transactional audit and recheck authority after audit persistence. Counts and rows use the same projection.

`npm run test:decision-inbox` validates the lifecycle, four formats, independent recipient/read state, current original membership, vote-only group participation, hierarchy movement, audit rollback/expiry and HTTP/SQL boundaries in a disposable database. `npm run test:decision-inbox:browser` additionally verifies exact-record navigation, actual participation, queue refresh, sibling denial and both languages/themes at four widths.

## Private operational channels

Migration 16 adds `/channels` for group or regional text conversations. It reuses the console layout, semantic palette, form/button/card primitives and scoped membership boundary. The retained broadcast-message editor represents a different workflow; its legacy endpoints are not enabled by this change. A channel is attached to a unit; the browser offers only eligible units and no organization selector.

Four explicit permissions govern the channel: `channel.read`, `channel.post`, `channel.manage` and `channel.moderate`. Reading is required in addition to each specialized permission. Position names and hierarchy rank confer no access. Subtree grants can deliberately authorize regional or council oversight; ordinary group members can receive read/post without management/moderation. Current authorized members can read the channel's existing history. Moving a unit invalidates the stored ancestry and closes access until a separately reviewed migration policy exists. Channel creation, archiving and moderation resolution retain fresh step-up requirements; existing local demo reauthentication supplies these without weakening production gates.

The initial journey includes creation, active/unread/archived lists, text up to 4,000 characters, same-channel replies, explicit read acknowledgement, mute/unmute, own-message removal, reporting and independent moderation. Replies refer to a sequence number without duplicating the original body. Messages use channel-local participant labels and expose neither a member directory nor account identifiers. Reports disclose neither the reporter identity nor additional profile fields. An author or reporter cannot resolve that report, even with moderation permission. Removing a message erases its canonical body while preserving its conversation position. This is logical deletion from application storage, not guaranteed physical erasure from PostgreSQL pages, WAL or backups; backup retention remains a release concern.

Each write has a retry key and a server-keyed digest of the validated command. Receipts store only result identifiers, never message text. An uncertain browser response can retry the unchanged command without duplicating messages. Strict HTTP validation rejects client-supplied actor fields; SQL independently enforces identity, scope, lifecycle, same-channel references and independence. The runtime role cannot access channel tables or internal projections directly. Organization/audit locking and a second authority check after audit prevent expiry or audit failure from leaving a committed write.

Read state is a monotonic sequence watermark: acknowledging the displayed page also acknowledges its earlier prefix, but never newer arrivals. Muting suppresses the channel's unread count without changing history or read state. Channel counts are separate from the administrative bell. Archive is versioned; new posts are denied until explicit reopening. Limits are 50 active standalone channels per unit and 20 posts per author/organization per minute; task conversations have a separate one-per-task constraint. Message history uses 40-record keyset pages; channel and moderation lists use 25-record pages. The foreground browser polls every 15 seconds and refreshes on focus/mutations; push delivery is not implemented. This serialized development implementation is not a measured concurrency or scale claim.

## Task-linked conversations

Migration 18 attaches an optional immutable WorkItem reference to the existing channel. There is at most one conversation per task and organization, enforced by a composite foreign key and unique index. A current task manager with explicit channel management/read permissions can create it from the task detail. Reading the task does not create a conversation. Retrying creation or a second authorized manager's creation request returns the same channel. Child tasks have independent conversations; messages are never copied between parent and child.

Both boundaries apply on every operation: current `channel.read` plus the existing Work contributor rule (scoped task management, or current `workitem.read`/`workitem.participate` with an assigned, in-progress, submitted or verified assignment). Applicants, reserve candidates, withdrawn/rejected participants and observers do not gain access from a broad channel grant. Posting, moderation and management also require their explicit channel permissions; task channel management requires current task management. Ancestry movement or loss of either domain's authority closes access, including history. Retaining a verified assignment alone does not bypass revoked membership or permissions.

The channel displays the canonical task title. Completed or cancelled tasks make their conversations read-only and put them in the archived view without changing the channel archive flag or copying task lifecycle state. Current authorized readers can still read history, manage their read/mute state, remove their own text or report/moderate existing content. New posts and reopening are denied. All existing reply, erasure, independent-review, audit rollback, post-audit authorization and retry protections remain in force.

The task detail opens the exact conversation through transient navigation state. **Back to task** returns to the exact authorized task, including records outside the current list filter. IDs stay out of URLs, and the destination rechecks server authority. Uncertain creation responses retain the immutable retry command; late responses after the task view unmounts cannot redirect the user.

`npm run test:work-channels` uses a disposable database to cover cross-domain permissions, concurrent creation, assigned-versus-applicant access, withdrawal, both task closure states, separate child conversations, moved ancestry, audit rollback, permission expiry and SQL/HTTP boundaries. `npm run test:work-channels:browser` adds real Chrome creation/open/return journeys, sibling-region isolation and language/theme/viewport checks. No external delivery, attachment storage or mobile UI is introduced.

## Temporary writing restrictions and independent appeals

Migration 19 adds a channel-local restriction record to the existing communication engine. A moderator with current explicit channel read/moderation authority selects an existing, unremoved message; the server derives its author. The client cannot supply a target member identity. The moderator must be neither that author nor a reporter of that message. The record has a mandatory reason and expiry, capped at thirty days. The UI offers one hour, one day, seven days and thirty days. One active restriction per subject/channel is enforced under the existing organization/advisory lock; repeat requests use existing keyed receipts. Archived channels and closed task channels cannot receive new restrictions.

The restriction affects posting in that channel only. It does not revoke membership, change task assignments, suppress history or grant another role access. A restricted member retains current authorized reading, read/mute state, own-message removal, reporting and appeal access. Expiry is evaluated against the database clock on each operation; no scheduler or client clock grants permission. Lifting a restriction restores posting only if all other membership, channel, task and lifecycle checks still permit it. Task-linked records remain subject to current Work contributor authority; lost authority and moved ancestry hide their records as well as their messages.

The affected member may submit one appeal per restriction, including an expired restriction for historical correction. Current scoped moderators can see the record; only an independent reviewer can act. The reviewer must be neither the affected member, the restriction issuer nor a reporter of the originating message. A reasoned decision either upholds the original expiry or lifts the restriction; it cannot extend the term. Lifecycle versions 1 (issued), 2 (appealed), 3 (reviewed) reject stale decisions. Database constraints/triggers preserve the original restriction and append its appeal/decision once. New restrictions and review decisions require fresh step-up; the member's appeal requires the current session and scope.

On `/channels`, **Restrictions and appeals** provides **Needs review**, **My restrictions** and **Restriction history**, with 25-record pagination and the same visibility predicate for rows/counts. This is the dedicated scoped moderation queue; migration 20 also projects eligible notices into the administrative inbox/bell as described below. Ordinary read/post members see only their own records; moderators see only their authorized channels. Queue entries show channel-local participant labels, reasons, expiry and appeal decisions, without account IDs, a member directory or copies of original message text. Reasons are visible to the affected member and authorized moderators, so the form asks for decision-relevant information only. Canonical text stays in the restricted record; retry receipts and audit metadata contain identifiers, not reason/appeal text. External delivery and retention/erasure policy for moderation text remain separate release work.

The wrapper reuses the existing channel command for content operations. Direct runtime execution of that internal function is revoked, so posting cannot bypass the new check. Both new and existing operations retain transactional audit, post-audit authorization and current-session checks. Audit failure or authority expiry before commit rolls back the transition. Web forms require explicit confirmation, preserve the immutable command on uncertain responses and discard actionable state after denial/conflict. Foreground views refresh every fifteen seconds when no action is being edited.

`npm run test:channel-restrictions` covers independent roles, ordinary-member disclosure, concurrent retries, channel isolation, actual expiry, historical integrity, audit failure, grant expiry, hierarchy movement, Work authority and SQL/HTTP boundaries in a disposable database. `npm run test:channel-restrictions:browser` exercises restriction → member appeal → independent review through real scoped accounts and checks both languages/themes and four viewport widths. Permanent platform bans and personal blocking are not represented by this temporary channel restriction.

`npm run demo:channels` adds bounded channel grants to the six existing synthetic accounts without resetting credentials or business records. `npm run test:channels` creates its own disposable database; tests cover scoped and ordinary-member access, retries, audit rollback, permission expiry, hierarchy movement, read/mute races, independent moderation, HTTP boundaries and history/rate limits. `npm run test:channels:browser` adds a four-account Chrome journey, language/theme/viewport checks and second-region isolation. Unit tests cover uncertain retries, stale responses, revoked-access cleanup, text escaping and confirmation.

## Moderation notices in the shared inbox

Migration 20 adds the **Channel moderation** category to the existing inbox and global bell. It projects the canonical restriction without copying message bodies, channel titles, reasons, appeal text or participant identities into previews. The affected member and current authorized issuer receive notices; independent current moderators receive appealed records. The issuer, affected member and originating reporter never receive a review action. Completed decisions remain visible to eligible recipients, while current channel scope, membership, hierarchy and Work contributor checks continue to govern every read. Channel-only members can discover their own inbox without an unrelated administration grant.

Only the recipient's observed read version is stored in a new table referencing the restriction. Notice versions are separate from the three moderation record versions: issue is 1 (expired 2), appeal is 3 (expired 4), decision is 5 (upheld and expired 6). A lifted restriction stays at 5; later clock expiry cannot change its outcome. Expiry never closes an appeal, since historical correction remains permitted. Reading neither submits nor decides an appeal, removes an actionable review, nor consumes a future lifecycle version. Counts and rows share the same projection; audit failure and expiry during audit roll back acknowledgements.

Opening a notice fetches its exact restriction through current domain authorization, even outside the selected queue/page. Navigation uses transient state with no private IDs in the URL; viewing creates no read acknowledgement or moderation action. Denial clears the record and action controls. Confirmed moderation writes refresh the bell/inbox through the existing workflow event, and the existing focus/60-second refresh covers changes by other users and clock expiry. This is in-app projection and read tracking, not external push or a second delivery service.

`npm run test:moderation-inbox` validates recipients, independent review, disclosure, read-version races, actual expiry, audit rollback, permission expiry, hierarchy movement, ordinary channel-only membership, Work authority and HTTP/SQL boundaries in a disposable database. Its `:browser` variant exercises actual notice-to-record navigation and independent decisions; all records are synthetic. Contribution/recognition web acceptance follows this checkpoint before secure attachments.

## Contribution recipient notices

Recipient recognition notices are also available through migration 21. See the [Contribution contract](CONTRIBUTION.md#recipient-notices-and-web-acceptance): immutable awards/corrections, recipient-only current authority, generic previews, coarse dates and exact private-history navigation. They share the inbox/bell while preserving separate administrative proposal disclosure.

Only synthetic development data is appropriate at this checkpoint. Deployment-level encryption, key custody, retention/deletion, independent security review and production authentication remain release gates. No custom E2EE protocol, anonymous messaging guarantee, external delivery or mobile client support is claimed.
