# Scoped member directory

Migration 30 adds an operational member directory to the existing Organization module. **Members** provides one row per person, shared-name or exact full-code search, unit/subtree and role-name filters, membership-state filters, bounded pages and a member card. It does not introduce enrollment, an identity vault, a public directory or technical administrator authority.

Discovery requires both current `member.read` and `unit.read` at each disclosed membership unit. A position label or existing `superadmin` account role grants nothing. Council/regional/group scopes use the same canonical membership/permission/ancestry checks as the other modules. List, search, counts, unit options, detail and pagination use the same restrictions. Unknown/hidden member detail returns the same denial. Search names, member selectors and filters stay out of browser navigation URLs and audit payloads. Authenticated API queries carry the filters; request logging omits query strings. Responses are `no-store`; required audit and a fresh second read precede disclosure. Expired/revoked authority or failed audit cannot return the initial read's data.

`organization_member_labels` stores only explicitly shared organizational display names. It is keyed by organization/member, has no runtime direct table grants, and is serialized with authority changes. Migration does not copy account names, emails or identity fields. Existing unnamed members display an opaque reference and remain searchable by the exact full UUID; partial UUID enumeration is not supported. Authorized name substring search is bounded to 120 characters and applies only to already visible members. A real member's display-name sharing/editing workflow belongs to the future profile/enrollment contract. Local demo activation seeds only the six previously authorized synthetic labels.

Memberships remain canonical. Effective states are active, suspended, ended, expired, scheduled and inactive authority (retired position, mismatched bundle version or unavailable permission bundle). These describe the membership, not legal identity verification, device assurance or the technical account's global suspension/login history. A member may have several visible memberships; status and role filters match at least one visible record, while the card retains all visible records. Ended/expired local history does not expose memberships elsewhere. Current hierarchy moves change discovery scope; Work keeps its separate frozen-ancestry rules.

## Points and participation

Directory permission alone does not reveal points. An eligible current membership unit must also satisfy existing `contribution.read` for the viewer and `unit.read` for the subject. Totals sum only entries covered by those eligible unit/subtree contexts and current entry-unit contribution authority; overlapping grants do not double count. `null` means restricted, while zero means an authorized empty balance. The UI calls this **Points in visible scope**, not a global total or ranking. Selecting **Points and recognition** opens the existing Contribution page with transient member/unit state; its server remains authoritative and independently approved award/correction rules are unchanged. The selected member is prefilled for a subsequent recognition proposal, never automatically awarded.

Task participation requires current Work visibility and task-unit member discovery. Viewing another person's assignment also requires Work management or verification authority, matching the existing task detail policy. The card has paginated permitted assignments, statuses, participant-reported progress and a verified count. It omits private reports, message bodies, ballots, choices, biometrics and unrelated Activity. Opening a task uses the existing transient Work navigation and repeats Work authorization. This slice does not expose anonymous Decision participation histories.

**Propose position** opens the existing membership proposal form with a member reference. It does not grant or change membership, submit automatically or bypass independent approval. The receiving form uses its current server-approved position choices. A directory visit grants no new authority.

## Operation and boundaries

`npm run db:migrate` applies the schema. `npm run demo:members` explicitly adds a separate scoped `member.read` bundle/position/membership for the six existing development accounts and their synthetic labels. It preserves credentials and old grants/data; rerunning does not restore revoked or expired grants or overwrite labels. It grants no Work, contribution, membership-change or platform-security permissions. Production bootstrap remains separate and disabled pending the release gates.

Member and unit option pages contain 25 records and support pages 1–1000; unit options have independent search/pagination. Pagination is stable for unchanged data, not a snapshot across concurrent changes. Query correctness and local workflow tests do not establish production performance. Filter terms and detail selection remain in page memory. Focus/60-second refresh rechecks current access and clears failed/stale projections.

This slice intentionally preserves the original console's Card/Input/Select/Button, sidebar, list/filter/detail patterns. The legacy Profiles screen combines demographic discovery, account reset and identity-related operations; enabling it wholesale would cross this module's purpose and permissions. Those retained controls remain inactive pending their separate identity/platform contracts.

Migration 39 adds **Manage membership** on eligible member-card rows: reviewed transfer/position replacement and termination of one selected membership, with current two-scope permissions and active-task blockers. See [membership lifecycle](MEMBERSHIP_LIFECYCLE.md). Points and Activity remain preserved with their existing disclosure rules.

Remaining: real profile sharing/editing, explicit enrollment/identity assurance, suspension/resumption, coordinated multi-membership transfers, broader permitted Activity summaries and measured large-directory performance. Technical platform administration remains independent of organizational authority.

`npm run test:members` verifies the directory against a disposable database; `npm run test:members:browser` adds local Chrome workflows. See STATUS for actual activation and completed evidence.
